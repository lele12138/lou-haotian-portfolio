# Agent 为什么需要 Memory：从上下文窗口到长期协作

如果把大模型单独拿出来，它其实没有我们想象中那么稳定的“记忆”。

模型能够记住什么，主要取决于当前这次调用里放进了什么内容。对话结束、上下文被清空，或者重要信息被大量工具日志淹没以后，模型就可能失去之前建立的目标、约束和判断依据。

现在一些模型已经支持百万级的 Context Window，但“能够放进去”不等于“能够始终准确使用”。

随着上下文增长，模型可能出现几种变化：

- 记得最近发生的事情，却忽略较早的关键要求；
- 能找到某条信息，却无法在正确的决策中使用它；
- 被大量工具日志和中间结果干扰；
- 在压缩上下文时丢失重要约束；
- 忘记自己当前正在完成哪一步。

有一种常见的工程经验是：即使上下文窗口还没有真正填满，系统也会在使用到大约30%至50%时开始主动压缩、清理或重建上下文。

这个比例并不是所有模型统一适用的硬性阈值。它更像一个提醒：

> **上下文窗口的理论容量，不等于 Agent 的可靠记忆容量。**

所以，设计 Agent Memory 的重点不是把所有信息都塞进 Prompt，而是回答三个问题：

1. 当前推理必须看到什么？
2. 当前任务需要在外部保存什么？
3. 哪些知识值得跨会话长期保留？

我更愿意把 Agent Memory 分成三个层次。

```text
第一层：Active Context Window
当前这一步正在思考什么

第二层：Working State
当前任务已经做到哪里

第三层：Durable Memory
未来的任务还需要记住什么
```

三层 Memory 管理的是不同时间尺度，也应该采用不同的保存方式。

## 第一层：Active Context Window

Active Context Window 是模型当前能够直接看到的内容。

它通常包括：

- 用户的原始目标；
- 系统规则；
- 最近几轮对话；
- 当前需要使用的资料；
- 最近一次工具返回；
- 当前步骤的决策依据。

这是 Agent 最接近人类“注意力”的一层。

它的优势是读取速度快，不需要额外检索。缺点也很明显：容量有限，而且容易被无关内容污染。

假设一个代码 Agent 运行测试后，把上千行安装日志、警告和错误栈全部放回上下文。真正重要的内容可能只有：

```text
测试失败：用户为空时，getUserName 返回未处理异常
位置：src/user.ts:42
```

如果原始日志全部进入 Context Window，模型不仅浪费 Token，还可能忘记用户最初要求修改什么。

因此，Active Context 的最佳实践不是“尽量装满”，而是保持它足够小、足够新，并且与当前决策直接相关。

我会遵循几个原则：

- 始终保留用户目标和关键约束；
- 保留最近发生的状态变化；
- 长日志只提取结论、错误类型和关键行；
- 已经沉淀到文件中的内容不在对话里反复复制；
- 旧分支已经确认无效时，不继续携带它的完整推理；
- 压缩上下文时优先保留事实、决定和未完成事项。

Context Compaction 也不应该只是把旧对话压缩成一段泛泛的摘要。好的压缩结果至少需要回答：

```text
目标是什么？
已经完成什么？
当前状态是什么？
做过哪些重要决定？
哪些限制仍然有效？
下一步是什么？
哪些问题尚未解决？
```

Active Context 的核心不是容量，而是注意力分配。

## 第二层：Working State

如果 Active Context 是 Agent 的注意力，那么 Working State 更像它的工作台。

它保存的是当前任务在外部世界中的进度，例如：

- `plan.md`；
- `todo.md`；
- 当前生成的代码；
- 下载或提取的资料；
- 测试结果；
- 中间分析表；
- 当前任务状态；
- 已完成和未完成事项。

Working State 不需要始终放在 Prompt 中。Agent只需要在做决定时读取相关部分，在完成动作后更新对应状态。

例如，一个 Agent 正在完成一项包含十个步骤的任务。与其在每轮对话中重复完整计划，不如将计划写入外部文件：

```markdown
# 当前目标

完成用户登录模块的异常处理。

## 进度

- [x] 定位登录入口
- [x] 找到空用户异常
- [ ] 修改错误处理
- [ ] 补充测试
- [ ] 运行完整测试
- [ ] 输出变更说明

## 当前约束

- 不修改现有接口
- 保持错误码兼容
- 不处理无关格式问题
```

模型每次只需要读取这份状态，选择下一项任务，完成后再更新文件。

这比单纯依赖聊天历史可靠得多。

聊天记录描述的是“模型说过什么”，Working State 记录的是“任务现在是什么状态”。两者并不相同。

Working State 的最佳实践包括：

- 使用结构化文件保存计划和进度；
- 把中间产物保存到工作区，而不是长期占用上下文；
- 给每个任务建立唯一状态和明确完成条件；
- 记录重要决定以及作出决定的原因；
- 任务结束后归档或清理临时文件；
- 不把临时猜测直接升级为长期事实。

这一层解决的不是跨会话学习，而是让 Agent 在一次长任务中不丢失主线。

## 第三层：Durable Memory

Durable Memory 是跨会话存在的长期记忆。

它保存的不是某次任务的所有细节，而是未来仍然有价值的信息，例如：

- 用户长期偏好；
- 项目目录和命名约定；
- 已确认的业务事实；
- 容易重复踩坑的限制；
- 稳定的测试和交付流程；
- 多次验证有效的操作方法；
- 适合复用的 Skill。

长期记忆最容易出现的问题，是把它理解成“什么都保存”。

如果 Agent 把每次对话、每次尝试和每段日志都写入长期记忆，记忆库会很快变成新的上下文垃圾场。以后每次检索都会带回大量重复、过时甚至互相冲突的信息。

因此，Durable Memory 的关键不是存储，而是筛选。

我会用四个问题判断一条信息是否值得进入长期记忆：

1. 它以后还会重复使用吗？
2. 如果忘记它，Agent 是否容易再次犯错？
3. 它是已经确认的事实，还是当前猜测？
4. 它是否有明确来源和适用范围？

适合长期保存的是：

```text
这个项目必须使用某个测试命令
```

不适合长期保存的是：

```text
我怀疑这次失败可能与网络有关
```

前者是可复用规则，后者只是尚未验证的临时判断。

长期记忆还需要定期复查。项目会变化，模型能力也会变化。过去必须写进记忆的详细说明，可能在新模型中已经变成不必要的负担。

所以长期记忆的原则不是越多越好，而是：

> **只保存能够持续校正 Agent 行为的最小必要信息。**

## Memory 不是仓库，而是一套路由机制

把 Memory 分成三层以后，我逐渐意识到：Agent Memory 真正解决的不是“信息存在哪里”，而是“信息什么时候重新进入推理”。

同一条信息可以存在文件、数据库或长期记忆中，但如果 Agent 在需要时没有读取，它仍然等于不存在。

反过来，如果所有信息每次都自动进入上下文，记忆系统又会变成噪声生成器。

因此，一个完整的 Memory 机制至少包含四个动作：

```text
Write：什么信息值得写入
Store：保存在哪个层次
Retrieve：什么时候重新读取
Forget：什么时候压缩、归档或删除
```

Memory 设计不仅是记住，也是主动遗忘。

## Agent 为什么必须运行在循环中

当任务只需要生成一段文字时，模型可以一次完成。

但真正的 Agent 通常需要与外部环境交互。它必须先选择动作，使用工具，观察返回，再决定下一步。

可以把最基本的 Agent Loop 表达为：

```text
Choose
选择下一步动作
   ↓
Use
调用工具或执行操作
   ↓
Feedback
读取工具结果和环境变化
   ↓
Update
更新上下文与任务状态
   ↓
再次 Choose
```

这里最重要的不是让循环一直运行，而是让下一轮选择真正使用上一轮反馈。

例如，Agent 搜索一个文件，没有找到结果。下一步不应该机械地重复相同搜索，而应该根据反馈调整：

- 关键词是否写错；
- 文件是否在其他目录；
- 是否应该换成语义搜索；
- 任务假设是否一开始就不成立。

一个有效的 Loop 是不断缩小不确定性。

一个无效的 Loop 则只是不断重复动作。

所以每一轮循环最好都能回答：

```text
我刚刚知道了什么？
它改变了哪个判断？
下一步为什么与上一轮不同？
什么条件下应该停止？
```

## 工具卫生：不要让工具输出污染循环

Agent Loop 很容易被工具污染。

所谓工具污染，是指工具返回的大量原始信息进入上下文后，逐渐挤压目标、约束和关键状态。

常见污染包括：

- 上千行编译日志；
- 重复的搜索结果；
- 完整网页源码；
- 无关警告；
- 超长错误堆栈；
- 二进制或压缩内容；
- 已经读取过的相同文件；
- 多次重试产生的重复报错。

工具卫生的目标，是让工具返回的信息可以被使用，而不是让工具尽可能多地输出。

最佳实践包括：

- 默认限制工具输出长度；
- 错误日志优先提取错误类型、位置和关键上下文；
- 大型输出保存为文件，只把路径和摘要放入上下文；
- 搜索结果去重并保留来源；
- 工具返回采用稳定的结构化格式；
- 明确区分成功、失败、部分成功和未知状态；
- 重试时不要重复注入相同错误；
- 只有下一步真正需要时，才读取完整产物。

可以把工具输出分成两部分：

```text
进入 Active Context：
结论、关键证据、状态变化、下一步需要的信息

进入 Working State：
完整日志、原始数据、长文档、中间产物
```

工具卫生不是简单地删减信息，而是把信息放到正确的记忆层。

## 结构性约束：限制 Agent 怎样完成任务

仅靠自然语言告诉 Agent“请认真一点”，很难保证长循环始终稳定。

结构性约束是把任务要求转化为系统可以检查的形式，例如：

- JSON Schema；
- 明确的任务状态机；
- 最大循环次数；
- 时间和成本预算；
- 文件长度或函数规模限制；
- 依赖方向；
- 必须通过的测试；
- 明确的完成条件；
- 固定的交付格式。

结构性约束主要解决的是 Agent 偏航。

模型可能在局部做出看似合理的选择，但经过几十轮循环后，任务方向可能逐渐偏离。结构性约束相当于给循环建立轨道：

```text
允许探索
但不能越过边界

允许调整方案
但不能改变目标

允许多次尝试
但必须受到预算限制
```

比较实用的原则是：

- 能由程序验证的，不只依赖模型自觉；
- 能写成测试的，不只写成提示词；
- 能写成 Schema 的，不依赖自由文本解析；
- 循环开始前定义完成条件；
- 达到停止条件后必须退出，而不是无限重试。

## 安全护栏：限制 Agent 能不能做

结构性约束关注“怎样完成”，安全护栏关注“哪些事情不能自动做”。

安全护栏可以按照操作风险分成三个等级：

| 等级 | 处理方式 | 例子 |
| --- | --- | --- |
| 低风险 | 自动执行 | 读取文件、搜索资料、运行只读检查 |
| 中风险 | 执行前确认或提供预览 | 修改文件、更新记录、发送普通消息 |
| 高风险 | 必须人工执行或专门审批 | 删除重要数据、付款、修改权限、不可逆操作 |

常见的安全护栏包括：

- 沙箱运行；
- 最小权限；
- 读写工具分离；
- 高风险操作人工确认；
- 写操作使用唯一请求标识；
- 限制调用次数和执行时间；
- 未知状态下停止后续操作；
- 外部内容不能自动改变系统规则；
- 执行结果由外部系统验证。

护栏的目标不是阻止 Agent 工作，而是让自动化程度与风险相匹配。

## 多 Agent 不是把上下文窗口简单相加

当一个 Agent 的 Context Window 不够用时，一个很自然的想法是：拆成多个 Agent 并行完成。

每个 Agent 拥有自己的上下文窗口，看起来总容量变大了，任务还能同时推进。

但多个上下文窗口并不等于一个更大的共同大脑。

> **多 Agent 增加的是局部上下文容量，不会自动增加共享理解。**

假设三个 Agent 分别负责调研、实现和测试。它们确实可以并行工作，但也会产生新的问题：

- 每个 Agent 看到的背景不同；
- 对目标和术语的理解可能不一致；
- 同一事实可能被保存成多个版本；
- 一个 Agent 作出的决定，其他 Agent 未必知道；
- 中间过程无法完整交接；
- 最终调度者需要重新读取和合并全部结果。

如果每个 Worker 输出五千字，Orchestrator 最后仍然要面对一万五千字的新上下文。信息没有消失，只是从一个窗口转移到了多个窗口，再集中到合并阶段。

这也是多 Agent 有时不如单 Agent 的原因。

## 为什么单 Agent 反而可能表现更好

单 Agent 的优势是拥有一条连续的决策历史。

它知道：

- 为什么选择当前方案；
- 哪些路线已经失败；
- 哪些假设已经被否定；
- 用户后来修改了哪些要求；
- 当前结果与最初目标之间有什么关系。

多 Agent 在交接时，往往只能传递结论，无法完整传递形成结论的过程。

这会带来几类损耗。

第一类是**信息压缩损耗**。Worker 为了控制输出长度，会省略它认为不重要的细节，但这些细节可能恰好是下一位 Agent 需要的。

第二类是**语义漂移**。不同 Agent 会使用不同术语、假设和判断标准。

第三类是**重复劳动**。多个 Agent 可能分别读取相同文件、搜索相同资料，反而增加成本。

第四类是**协调开销**。拆解、分配、等待、交接、复核和合并本身都需要时间与上下文。

第五类是**错误传播**。上游 Agent 输出了一个未经验证的结论，下游 Agent 可能把它当成事实继续推理。

所以多 Agent 并不是解决长上下文问题的默认答案。

很多时候，更有效的方案是：

```text
一个 Agent
+ 精简的 Active Context
+ 外部 Working State
+ 按需检索的 Durable Memory
```

## 什么情况下适合使用多 Agent

多 Agent 更适合真正能够独立完成的任务，例如：

- 分别调研互不依赖的资料来源；
- 针对多个文件执行同类检查；
- 同时运行不同实验；
- 一个 Agent 执行，另一个 Agent 独立审查；
- 任务有明确的 Orchestrator–Worker 结构。

不适合并行拆分的情况包括：

- 后续任务依赖前一步的判断；
- 所有子任务都需要完整了解用户意图；
- 决策需要不断相互协商；
- 不同 Agent 会修改同一份状态；
- 最终合并比原任务本身还复杂。

判断是否需要多 Agent，可以先问：

> 子任务之间是否真的独立？

如果答案是否定的，那么增加 Agent 数量很可能只是增加交接次数。

## 多 Agent 的 Memory 最佳实践

如果确实需要多 Agent，我认为 Memory 设计比 Agent 数量更加重要。

第一，应该有一个明确的顶层 Orchestrator。它负责维护任务目标、依赖关系和唯一的权威状态。

第二，每个 Worker 只接收完成自己任务所需的最小上下文，不复制整个主会话。

第三，Agent 之间通过结构化产物交接，而不是互相转发完整聊天记录。例如：

```json
{
  "task": "检查认证模块",
  "status": "completed",
  "findings": [],
  "changed_files": [],
  "evidence": [],
  "open_questions": []
}
```

第四，完整产物进入共享 Working State，交接消息只包含摘要和引用位置。

第五，关键事实只能有一个权威来源。多个 Agent 可以提出建议，但不能各自维护一份互相冲突的任务状态。

第六，限制同时运行的 Agent 数量。并行度越高，协调、冲突和合并成本也越高。

第七，保留单 Agent 基线。只有在相同任务上证明多 Agent 带来质量、速度或成本收益，才值得引入额外编排。

可以把原则概括为：

```text
默认使用单 Agent 保持连续性
任务真正独立时再并行
通过文件共享事实
通过结构化契约交接
由一个 Orchestrator 维护权威状态
```

## 我现在怎样理解 Agent Memory

Agent Memory 不是让模型记住一切。

真正好的 Memory 系统，会主动决定：

- 什么应该留在当前注意力里；
- 什么应该写入外部工作状态；
- 什么值得沉淀成长期规则；
- 什么应该被压缩、归档或遗忘；
- 哪些信息应该提供给哪个 Agent；
- 多个 Agent 如何共享事实而不共享混乱。

同样，Agent Loop 也不是让模型无限地“思考—调用—重试”。

好的 Loop 应该不断读取反馈、更新状态、缩小不确定性，并在达到目标、预算耗尽或风险上升时停止。

最终，Memory、Loops 和 Multi-Agent 其实在解决同一个问题：

> **怎样让一个容易丢失主线的概率模型，在长时间、多步骤和不断变化的任务中，仍然保持连续、可控并且可验证的行为。**

上下文窗口再大，也不能代替记忆设计。

Agent 数量再多，也不能代替清晰的状态与交接。

真正决定系统长期表现的，不是它能一次读进多少 Token，而是它是否知道：现在该关注什么、过去什么仍然有效、下一步依据什么行动，以及完成以后如何证明结果。
